# 04 - 规则引擎设计

## 一、定位

规则层是异常检测的第一层，负责从访问日志中识别行为特征明显的攻击（DDoS、爆破、扫描）。核心思路：把请求级日志聚合成 IP 级行为画像，用可配置阈值逐 IP 判定，将结论回写到该 IP 的所有日志行，并生成可解释的告警。

规则层输出：

- `access_log.rule_abnormal` / `rule_type`：规则判定结果；
- `access_log.final_abnormal`：规则与模型的合并结果（`rule_abnormal OR model_abnormal`）；
- `alert`：每个异常 IP 一条，`alert_source = 'rule'`（模型也命中时升级为 `both`）；
- `upload_task.rule_detect` / `rule_detail`：规则检测状态（0 未检测，1 检测中，2 完成，3 失败）与 JSON 摘要。

规则层不修改 `model_score` / `model_abnormal`。

## 二、检测流程

```
access_log（按 upload_task_id 取本次任务日志）
      │ 按 IP 聚合
      ▼
IpFeature（IP 级特征）
      │ RuleEngine 逐条规则判定
      ▼
Map<IP, List<RuleHit>>
      │ 独立事务写回
      ▼
access_log 标记 + alert
```

1. Controller 先同步校验任务（存在、状态为完成、成功行数大于 0）并原子抢占：`rule_detect` 0/2/3 → 1，已是 1 则返回 409；
2. 抢占成功后立即返回「规则检测已提交，正在后台执行」，检测在 `@Async` 线程中执行；
3. 执行聚合 SQL，得到每个 IP 的特征；
4. 对每个 IP 执行全部规则，收集命中的规则及指标描述；
5. 写回：重置该任务的规则标记 → `both` 退回 `model` → 删除规则告警 → 与模型告警合并（复用行改为 `both`，其余插入 `rule`）；
6. 成功置 `rule_detect=2` 并写入 `rule_detail` JSON，异常置 `rule_detect=3`（摘要为 NULL）后记录日志；
7. 前端轮询 `GET /uploadTask/polling?taskId=` 观察状态与摘要。

`upload_task.status` 始终只表示上传解析生命周期（0/1/2），检测状态由 `rule_detect` / `model_detect` 独立表达。完成或失败的任务可以重新检测，检测中的任务不可重入。

## 三、特征聚合

按 IP 聚合，一次 SQL 完成：

```sql
select ip,
       count(*)                                                   as total_requests,
       max(access_time)                                           as last_access_time,
       sum(case when status_code = 404 then 1 else 0 end)         as count404,
       sum(case when status_code in (401, 403) then 1 else 0 end) as auth_failure_count
from access_log
where upload_task_id = #{taskId}
group by ip
```

分钟峰值单独按分钟分桶后取最大值，再通过 IP 左连接：

```sql
select ip, max(cnt) as peak_per_minute
from (select ip,
             date_format(access_time, '%Y-%m-%d %H:%i') as minute_bucket,
             count(*)                                   as cnt
      from access_log
      where upload_task_id = #{taskId}
      group by ip, minute_bucket) b
group by ip
```

对应 `IpFeature` 字段：

| 字段 | 含义 |
| --- | --- |
| `ip` | 源 IP |
| `totalRequests` | 总请求数 |
| `lastAccessTime` | 最后访问时间（用作告警触发时间） |
| `count404` | 404 次数 |
| `authFailureCount` | 401 + 403 次数 |
| `peakPerMinute` | 单分钟最大请求数 |
| `getRatio404()` | `count404 / totalRequests` |
| `getAuthFailureRatio()` | `authFailureCount / totalRequests` |

占比均以该 IP 自身的总请求数为分母，避免攻击行为被整体良性流量稀释。

## 四、规则模型

```java
public interface Rule {
    String type();
    boolean match(IpFeature feature);
    String describe(IpFeature feature);
}

public record RuleHit(String type, String description) { }
```

`RuleEngine` 注入 `List<Rule>`，对每个 IP 执行所有规则：

```java
public List<RuleHit> evaluate(IpFeature feature) {
    return rules.stream()
            .filter(rule -> rule.match(feature))
            .map(rule -> new RuleHit(rule.type(), rule.describe(feature)))
            .toList();
}
```

- `match()` 每条规则都执行，`describe()` 只在命中时调用；
- 返回列表只包含命中的规则，长度 0–3，顺序由 `@Order` 决定（10 高频、20 大量404、30 认证失败）；
- 新增规则只需新建一个 `Rule` 实现并加配置，引擎不用修改。

## 五、规则定义

| 规则 | `type` | 判定条件 | 默认阈值 |
| --- | --- | --- | --- |
| `HighFrequencyRule` | 高频访问 | `peakPerMinute >= 60 && totalRequests >= 60` | 60 次/分钟、60 次 |
| `ScanRule` | 大量404 | `count404 >= 10 && ratio404 >= 0.20` | 10 次、20% |
| `AuthFailureRule` | 认证失败 | `totalRequests >= 20 && authFailureRatio >= 0.50` | 20 次、50% |

每条规则同时限制绝对量和占比：绝对量避免低流量 IP 被少量错误码误判，占比避免大流量正常 IP 被零星错误码误判。

- 401 和 403 在认证失败规则中不区分，SQL 直接合并计数；明细仍保留在 `access_log`；
- 慢响应规则已移除：当前合成数据没有真实慢速攻击样本，开启只会误报；待数据生成修正后再恢复。

## 六、结果写回与告警

写回由独立 Bean `RuleResultWriter` 在事务内完成：

1. 重置该任务：`rule_abnormal = 0`、`rule_type = NULL`、`final_abnormal = model_abnormal`；
2. 把 `alert_source = 'both'` 的行退回 `'model'`，再删除 `alert_source = 'rule'` 的行；
3. 剩余的告警全部是模型层告警，按 IP 建立索引；
4. 对每个命中 IP：更新其全部日志行 `rule_abnormal = 1`、`rule_type = 命中类型`、`final_abnormal = 1`；若该 IP 已有模型告警，则复用该行改为 `both` 并写入规则内容；否则插入一条 `rule` 告警：

| 字段 | 取值 |
| --- | --- |
| `task_id` | 上传任务 ID |
| `ip` | 异常 IP |
| `alert_type` | 命中规则类型拼接，超过 50 字符写「多规则命中」 |
| `alert_source` | `rule`（模型也命中时为 `both`） |
| `description` | 各规则指标描述用「；」拼接，截断 500 字符 |
| `trigger_time` | 该 IP 最后访问时间 |
| `status` | 0（未处理） |

「先重置、再删除、再合并」保证同一任务重复检测结果一致（幂等），且规则重跑不会删除模型独有的告警；`(task_id, ip)` 唯一约束靠「复用行 `updateById` / 新行 `insert`」避开。聚合与规则计算在事务外，只有写回在短事务内。

检测状态由 `DetectServiceImpl` 在写回事务之外维护：成功置 `rule_detect=2` 并写入 `rule_detail` JSON，异常置 `rule_detect=3`、摘要置 NULL；失败状态更新本身出错时只记录日志，不覆盖原始异常。检测由 `@Async` 线程执行，接口在抢占成功后立即返回。

## 七、接口设计

### 7.1 请求类型

```
POST
```

### 7.2 请求格式

```
POST /Detect/runRule?taskId={taskId}
Authorization: Bearer <token>
```

- 无请求体，任务 ID 通过 query 参数传递；
- 需要 JWT 登录后的 token；
- 接口只做校验与抢占，检测在后台 `@Async` 线程执行，立即返回「规则检测已提交，正在后台执行」。

示例：

```bash
curl -X POST "http://localhost:8080/Detect/runRule?taskId=6" \
  -H "Authorization: Bearer <token>"
```

参数校验：

| 场景 | 返回 |
| --- | --- |
| 任务不存在 | `404 上传任务不存在` |
| 任务未完成 | `409 上传任务尚未完成` |
| 成功行数为 0 | `404 没有可检测的数据` |
| 该任务已有检测在进行 | `409 该任务正在检测中` |

同一任务并发触发检测时，只有第一个请求能完成 `rule_detect` 的原子抢占，其余请求返回 409。

### 7.3 返回示例

提交成功：

```json
{
  "code": 200,
  "msg": "规则检测已提交，正在后台执行",
  "data": 6
}
```

检测结果通过轮询获取：

```
GET /uploadTask/polling?taskId=6
```

返回的 `UploadTask` 中与本层相关的字段：

| 字段 | 含义 |
| --- | --- |
| `ruleDetect` | 0 未检测 / 1 检测中 / 2 完成 / 3 失败 |
| `ruleDetail` | 成功时的 JSON 摘要，抢占时清空 |

`ruleDetail` 示例：

```json
{"ipCount":145,"abnormalIpCount":38,"elapsedMs":1594,"finishedAt":"2026-11-20 19:02:11"}
```

失败：

```json
{
  "code": 409,
  "msg": "上传任务尚未完成",
  "data": null
}
```

## 八、配置项

```yaml
my-config:
  detect-rules:
    high-frequency:
      enabled: true
      peak-per-minute: 60
      min-total: 60
    scan:
      enabled: true
      min-404: 10
      min-ratio: 0.2
    auth-failure:
      enabled: true
      min-total: 20
      min-ratio: 0.5
```

阈值由 `config/DetectRuleConfig` 绑定，修改配置即可调整规则，不需要改代码。
